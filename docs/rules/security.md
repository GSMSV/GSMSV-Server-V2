# 보안 규칙

## 공개 저장소

- 비밀값(토큰·비밀번호·키), 내부 IP, 포트, 서버 주소를 코드·커밋·이슈·PR·댓글에 쓰지 않는다
- 비밀값을 실수로 올렸으면 커밋만 지우고 넘어가지 않는다. 바로 사용자에게 알린다 (교체가 필요하다)
- 보안 문제는 공개 이슈로 쓰지 않는다 ([SECURITY.md](../../.github/SECURITY.md))

## 권한 판단 Layer (22번)

자세한 내용은 팀 Notion 기능명세서 22번. 어기면 보안 사고로 이어진다.

- 권한 판단은 이 서버의 **로더에서만** 한다. Infra-V2(Go)에는 권한 판단 코드를 두지 않는다. Infra 호출은 로더를 통과한 뒤에만 한다
- 로더는 3종이다 (`com.gsmsv.api.global.authorization`)
  - **서비스 자원 로더** (GRN): 파서 검사 → id로 DB 1회 조회 → DB 값으로 GRN을 다시 만들어 요청 GRN과 통째로 비교(다르면 404) → 규칙표 판단
  - **하위 자원 로더** (부모 GRN + 하위 id): 부모를 위 과정으로 통과시킨 뒤 하위 자원을 찾고, 실제 부모가 요청의 부모와 같은지 확인
  - **팀 전용 로더** (팀 id): 같은 규칙표로 판단하고 감사 로그를 남긴다
- 목록 조회는 같은 규칙표를 쓰는 `listVisible(user)`만 쓴다
- 결과: 허용이면 자원 객체, 볼 수 없으면 **404**, 볼 수 있지만 권한이 없으면 **403**
- 판단 순서: DB의 소유자(개인/팀) → 그 팀에서 요청자의 역할 → 규칙표 대조. 팀 멤버십은 캐시하지 않는다

### 규칙표 (21번)

| 누가 | 할 수 있는 것 |
|---|---|
| 팀원 전원 | 조회, SSH 명령어·비밀번호 보기, 연장 |
| 팀장·DevOps | 생성·삭제·전원·사양 변경·스냅샷·포트포워딩·방화벽·도메인 |
| 팀장만 | 초대·제외, DevOps 부여, 팀 해체, 팀장 넘기기 |
| 관리자 | 같은 관문을 지나 "모든 동작 허용" 규칙으로 통과 |
| SYSTEM | 내부 동작 전용 |
| 개인 자원 소유자 | 본인 자원에 모든 동작 (v1과 동일) |

- 소유는 개인·팀 2종뿐이다. 개인 자원을 팀 자원으로 바꾸지 못한다 (소유자 필드 변경 불가). 자원 단위 공유 기능은 없다

### 코드 규칙

- 서비스 자원 repository의 id 조회는 로더와 `listVisible` 밖에서 호출하지 않는다
- service는 id가 아니라 **로더가 돌려준 자원 객체**를 받는다
- controller·service에서 소유자·역할을 직접 비교하지 않는다

## GRN 규칙 (23번)

- 서비스 자원 `grn:{소유자 id}:{자원 id}`, 하위 자원 `{부모 GRN}/{하위 id}`
- id는 `{접두사}-{무작위}`. 허용 문자 `0123456789abcdefghjkmnpqrstvwxyz` (i, l, o, u 제외). 서비스 자원·사용자·팀은 12자, 하위 자원은 8자
- 서비스 자원 정규식: `^grn:(user|team)-[0-9a-hjkmnp-tv-z]{12}:(vm|fn|db|deploy)-[0-9a-hjkmnp-tv-z]{12}$`
- **소유자 칸은 표시용이다. 권한 판단에 쓰지 않는다**
- GRN에 노드, vmid, 사양, 사용자가 정한 이름을 넣지 않는다
- 파서는 이 저장소(`com.gsmsv.api.global.grn`)에 구현하고 Contracts-V2에는 정의만 둔다
- 파서는 정규식으로 문자열 전체를 검사하고 **자원 id만** 돌려준다. 소유자 칸 값은 파서 밖으로 꺼내지 않는다
- **GRN 문자열을 직접 자르지 않는다** (`split`, `substring` 등 금지). 항상 파서를 쓴다
- 형식 오류(정규식 불일치)는 400. 존재 여부를 드러내지 않으므로 안전하다
- 형식은 맞지만 엔드포인트와 자원 종류가 다르면(예: VM API에 `fn-` GRN) 400
- 파서 테스트는 Contracts-V2의 맞는/틀린 id 목록을 그대로 쓴다
