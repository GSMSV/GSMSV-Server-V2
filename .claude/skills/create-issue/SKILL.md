# create-issue

GitHub 이슈를 만든다. 제목 형식과 라벨은 [AGENTS.md 1장](../../../AGENTS.md)을 따른다. 이 문서에는 절차와 본문 구조만 둔다.

## 1. 내용 정하기

- 사용자에게 무엇을 할지, 버그인지 작업·기능인지 확인한다. 빈 이슈는 만들지 않는다
- 작업·기능은 구현 방안을 이슈에서 정한다. 관련 코드와 계약을 읽고 방안을 제안한 뒤 사용자와 맞춘다. 구현할 때 다시 조사하지 않도록 바뀌는 클래스와 흐름까지 적는다
- 비밀값·내부 IP·포트·서버 주소가 들어가지 않게 한다. 보안 문제면 이슈를 만들지 않고 `.github/SECURITY.md`대로 비공개로 알리라고 안내한다
- 비슷한 이슈가 이미 있는지 확인한다

```bash
gh issue list --state open --search "<키워드>"
```

## 2. 제목과 라벨

- 제목: `타입(scope): 한국어 설명` (AGENTS.md 1.2). 이슈 제목에는 `!`를 쓰지 않는다
- 라벨: 타입별 값 (AGENTS.md 1.3). 양식의 기본 라벨이 아니라 제목의 타입을 따른다

## 3. 본문

양식 원본은 `.github/ISSUE_TEMPLATE/`다. `gh issue create`로 만들면 양식이 적용되지 않으므로 본문을 직접 쓴다. 양식이 바뀌었을 수 있으니 매번 `task.yml`·`bug.yml`을 읽고 칸 이름을 맞춘다.

- 버그(`fix`)는 `bug.yml`, 그 밖의 타입은 `task.yml` 구조를 쓴다
- 첫 줄에는 양식 맨 위의 안내 문구를 그대로 둔다
- 쓸 내용이 없는 칸은 `없음`이라고 적는다. 칸을 지우지 않는다
- 필요하면 마지막에 `### 참고`를 붙여 관련 이슈·선행 작업을 적는다

작업·기능 (`task.yml`):

```markdown
> 비밀값·내부 IP·포트 같은 운영 정보는 적지 않는다 (공개 저장소).

### 관련 기능

기능 번호와 이름 (예: 23번 자원 이름 규칙). 없으면 없음

### 무엇을

할 일. 항목이 여러 개면 체크리스트(- [ ])로 쓴다

### 구현 방안

핵심 기능을 어떻게 만들지. 코드 전체가 아니라 아래만 적는다
- 바뀌는 곳: 패키지·클래스 이름
- 흐름: 요청 → 로더 → service → repository 순서로 무엇을 하는지
- 정할 것: 고른 방식과 이유, 다른 안을 버린 이유

### 완료 조건

이게 되면 끝이라고 할 수 있는 문장 1~2개
```

버그 (`bug.yml`):

```markdown
> 비밀값·내부 IP·포트 같은 운영 정보는 적지 않는다 (공개 저장소).

### 무슨 일이 있었나

실제로 일어난 일. 에러 메시지가 있으면 붙인다 (운영 정보는 지운다)

### 기대한 동작

원래 어떻게 돼야 하는지

### 재현 방법

1. 순서대로 적는다

### 수정 방안

원인·고칠 곳·고치는 방법. 모르면 없음
```

## 4. 만들기

본문은 저장소 밖 임시 파일에 쓰고 `--body-file`로 넘긴다 (저장소 안에 파일을 만들면 커밋에 섞일 수 있다).

```bash
gh issue create --title "feat(vm): VM 생성 API" --label enhancement --body-file <임시 본문 파일>
```

`check-git-format.mjs` hook이 제목을 검사한다. 막히면 메시지대로 고쳐 다시 실행한다.

## 5. 보고

이슈 링크와 번호를 알려준다. 이어서 작업한다면 브랜치 이름을 `타입/이슈번호-설명` 형식으로 제안한다.
